# 社区健身赛事数据服务

本项目为社区健身活动提供从报名、评分、现场签到、便民服务记录到成果发布的 FastAPI 接口。业务数据保存在本地 SQLite；演示样本均为合成数据，不代表真实参赛者或活动统计。

## 启动与验证

在已安装 requirements.txt 锁定版本的 Python 环境中运行：

    uvicorn community_fitness.api:app --host 127.0.0.1 --port 8000

可设置 FITNESS_DB 环境变量选择数据库文件。接口说明位于 /docs。以下命令分别运行真实业务测试、语法检查和完整合成活动演示：

    python -m unittest discover -s tests -v
    python -m compileall -q community_fitness
    python -m community_fitness.demo

## 数据流程

在草稿阶段建立赛事、评分组、评分规则、队伍、裁判和服务专区。赛事开启后，每个组单独开启评分会话。裁判以请求键提交逐项分数；卡片修订使用预期旧版，并保留历史。只有组内全部有效裁判完成评分，队伍才参与排名。排名相同者共享名次；缺失评分不会当作零分。

现场签到以队伍内匿名成员标识去重，不能超过报名人数。专区记录分别保存接触次数、服务人次和匿名访客标识。批量导入逐行报告接收或拒绝结果，重复请求安全重放，同一记录 ID 的不同内容报告冲突。时间均须带明确偏移，专区接触必须落在开放区间内。

评分争议未解决时，组别评分会话无法关闭。所有会话关闭后才能关闭赛事。预览给出评分完整性、未决争议、服务统计和源修订号。发布时同时提交预期旧版与源修订号，防止并发更新覆盖结果。已发布版本保持不可变；迟到的服务记录可形成新版，但旧版查询及 CSV 导出继续返回原结果。

对账、准备状态、溯源、审计、分时统计与质量接口用于定位缺报、签到与服务记录。fixtures/ 中的本地样本仅用于演示与测试。

## 实时采集与对外版本的差异分析

`GET /events/{event_id}/publication-analysis` 面向运营值班：成果发布后仍会收到现场记录，实时统计与对外 CSV 不再相同，本接口说明差异的来历。

- **采集进度**（`collection`）：赛事状态、源修订号、审计序号上界，以及评分卡、服务记录、签到三条数据流各自已收到的记录数与最新时间。
- **对外可见版本**（`official`、`visible_version`）：当前发布版本、发布时间、发布时冻结的指标，以及默认导出和按版本导出各自使用的版本号。
- **差异归因**（`metrics.delta`、`attribution`）：每个变化指标给出对外值、实时值与增量，并指明由哪类变化驱动。`attribution.impact_map` 固定说明评分卡修订（名次、均分、中位数、分项）、现场晚到服务记录（服务记录数、人次、去重访客、专区与日期分布）与签到补记（签到人数、闸口、队伍）各自影响哪些指标。
- **逐条变化**（`changes`、`replays`、`standings_detail`、`services_detail`、`attendance_detail`）：按审计序号列出发布后的具体记录。`arrival=backfill` 表示记录发生在发布之前、只是补送；`new_after_publish` 表示发布后才发生。请求重放单独列出，不进入数据变化，也不影响任何指标。
- **提示**（`notices`）：区分正常版本滞后（`version_lag`）与真实质量异常（`unexplained_difference`、`scores_regressed`）。未结争议标记为 `contested`，并说明已发布版本仍对外可见但结果处于争议中。

**口径与边界：** 发布版本不可变，`summary.official` 只有在实时采集与对外版本完全一致时才为真；未发布数据一律带 `official: false`，不会被当作正式结果。新旧数据的分界取自发布审计记录的 `audit.seq`（与数据写入同一事务），因此在发布与现场记录同时发生或两台主机时钟不一致时仍能正确划分；缺少该审计记录时退回发布时间近似，并以 `boundary_ambiguous` 明确提示，而不是静默计入。读取整个视图时使用单个一致性读事务，避免并发发布造成版本与数据错配。
